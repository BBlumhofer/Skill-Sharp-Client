# Differences to the Python client

The client behaves like `opensmi-client` at `9026539`, except where this table says otherwise. Each row names the code
and the test that shows the behavior (tests in `tests/OpenSmi.Client.Tests`). When upstream fixes one of these, the C#
client follows.

| Python | C# | Code | Test |
|---|---|---|---|
| `start(wait=True)` waits only for Running or Completed | `StartWait.Completion` waits for Completed; for continuous skills it throws `InvalidOperationException` | `Enums.cs` (`StartWait`), `RemoteCallable.cs` (`RemoteSkill.StartAsync`) | `SkillTests.Finite_skill_runs_to_completion`, `SkillTests.Completion_wait_is_rejected_for_continuous_skills` |
| waits have no timeout | every wait takes a `timeout` (`TimeoutException`) and a `CancellationToken` | `RemoteCallable.cs` (`RemoteSkill.WaitForStatesAsync`) | `DeviationTests.Skill_wait_ends_with_timeout_or_cancellation_instead_of_hanging` |
| `RemoteUserData.user_level` is the lock priority as text | additionally `LockPriority` as number | `RemoteUser.cs` (`LockPriority`) | `SkillTests.Users_expose_lock_priority`, `ObjectModelTests.Users_belong_to_the_server` |
| return values of the lock methods are dropped | `LockResult` (`Ok`, `NotLocked`) | `RemoteLock.cs`, `Enums.cs` (`LockResult`) | `LockTests.Init_and_exit_lock` |
| a new client certificate on every connect | the certificate is created once in the store and reused | `SecurityOptions.cs`, `RemoteServer.cs` | `SecurityTests.Client_certificate_is_created_once_and_reused` |
| the server certificate is not checked, no trust store | checked against the trust store; `AutoAcceptServerCertificate` must be set explicitly | `SecurityOptions.cs`, `RemoteServer.cs` | `SecurityTests.Untrusted_server_certificate_fails_without_retry`, `SecurityTests.Server_certificate_in_trust_store_connects_without_auto_accept`, `SecurityTests.Encrypted_connect_with_auto_accept_browses_the_machine` |
| an unknown state raises `KeyError` (skills) or `UnknownStateError` (components) | both throw `OpenSmiUnknownStateException`, an `OpenSmiProtocolException` | `Sample.cs` (`SampleUpdates.ParseItemState`), `RemoteCallable.cs` (`RemoteSkill.ParseState`) | `SkillStateParsingTests.Unknown_state_text_is_a_protocol_error`, `SampleTests.Empty_item_state_is_null_and_unknown_throws` |
| skill and component states are `HALTED`/`None` with `BadWaitingForInitialData` until the first notification | the state is read once while browsing, before subscribing, so it is known when `ConnectAsync` returns | `RemoteCallable.cs` (`BrowseStateMachineAsync`), `RemoteComponent.cs` (`BrowseBuildingBlocksAsync`) | `BrowseModelTests.States_and_values_are_known_with_status_and_timestamps_after_connect` |
| `read_all` returns a dict by `variable.name`, while `write_all` and `[...]` take the segment | `ReadAllAsync` also returns the segment, so reading and writing use the same keys; for valid names both are equal | `RemoteVariableContainer.cs` (`ReadAllAsync`) | `ObjectModelTests.Names_from_other_servers_are_sanitized_and_suffixed` |
| `Requirements` is read only below `SkillExecution`; opensmi-server 0.3 puts it below the skill object, so `ua_depends_on` stays empty | skills read both places; checks do not inherit their skill's requirements | `RemoteCallable.cs` (`RequirementsOwner`, `BrowseDependenciesAsync`) | `SkillTests.Requirements_give_dependencies` |
| `read_all` and `write_all` read and write one variable after another | one read or write request; rejected values go through `WriteValueAsync` one by one | `RemoteVariableContainer.cs` (`ReadAllAsync`, `WriteAllAsync`) | `WriteTests.Write_all_writes_a_batch_and_rejects_unknown_names_before_writing` |
| `Signal` with `connect(handler)`, handlers run concurrently (`gather`) | `event AsyncEventHandler<T>`, handlers run one after another in subscription order, each failure is logged; plus `Watch…Async` streams (current value first, small buffer that drops the oldest values) | `AsyncEvents.cs`, `RemoteCallable.cs` (`WatchStateAsync`), `RemoteVariable.cs` (`WatchValueAsync`), `RemoteServer.cs` (`WatchStatusAsync`) | `EventTests`, `SkillTests.Watch_state_sees_running_and_completed` |
| unit names in upper case (`CENTIMETRE`) | PascalCase (`Unit.Centimetre`); `EUInformation.Description` keeps the Python name | `tools/generate_units.py`, `Unit.g.cs`, `Units.cs` | `UnitTests.Eu_information_round_trips_like_python` |
| custom data types are loaded at connect (`load_data_type_definitions`, enums and structures), an enum value is an `IntEnum` member | each variable with a custom data type reads its `DataTypeDefinition`, enums only: `ValidValues` maps `"0"` to the name, `Value` is the member name (`"Green"`); structures stay `ExtensionObject`; read errors are only logged | `RemoteVariable.cs` (`InitCoreAsync`) | `CustomTypeTests.Enum_variable_exposes_type_name_valid_values_and_member_name` |
| writing an enum member name fails (asyncua serialization error); a display name is written as key only after the server rejected it | a display name from `ValidValues` is mapped to its key before writing, also in `WriteAllAsync`; a value that cannot be converted throws `OpenSmiInvalidValueException` | `RemoteVariable.cs` (`ToWriteValue`) | `CustomTypeTests.Enum_variable_is_written_by_member_name_or_number` |
