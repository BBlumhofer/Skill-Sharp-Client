Pattern across all libraries: network clients for push messages have moved from synchronous handlers to Task-returning event delegates (MQTTnet 4, RabbitMQ 7, Azure IoT v2, SignalR, NATS connection events, Azure.Core). These delegates run sequentially from a single-reader queue away from the I/O thread. MQTTnet, SignalR and NATS build this the same way OpenSmi does today. Where someone needs to consume, wait or apply backpressure, `IAsyncEnumerable<T>` over a bounded channel is added (NATS, gRPC, SignalR streaming, Redis queue, OPC Foundation 2.0 explicitly for "state-machine waits"). Only Workstation.UaClient has `IObservable<T>` as its primary API; Orleans uses an async variant of it. None of the libraries uses System.Reactive as a dependency (I checked this for each one only through the types linked above and did not look for a package dependency: **unverified**).

## 2. What Microsoft recommends

- Framework Design Guidelines, events (2nd edition 2008, explicitly "may be out-of-date"; the 3rd edition is not online, **unverified** whether it changes anything): "DO use `System.EventHandler<TEventArgs>`", "DO use a return type of void for event handlers", with the reasoning that an event calls several handlers and there would otherwise be several return values. Also "DO NOT pass null as the sender", "CONSIDER using a subclass of EventArgs" (so that fields can be added later) and a protected virtual `On…` method for unsealed classes. According to usability studies, most developers cope better with events than with other callback mechanisms ([Event Design](https://learn.microsoft.com/en-us/dotnet/standard/design-guidelines/event)).
- Observer pattern docs (as of 2025-10): "Standard .NET events — For simple notification scenarios within a single application, events are more idiomatic and easier to implement." For async pull sequences "where the consumer controls the pace" they recommend `IAsyncEnumerable<T>`, for "backpressure and async support" channels, and for "complex event composition" System.Reactive instead of a custom `IObservable` implementation ([Observer design pattern](https://learn.microsoft.com/en-us/dotnet/standard/events/observer-design-pattern)).
- `async void` (Cleary, MSDN Magazine, reviewed by Stephen Toub): "Avoid async void" with a single exception, event handlers. Exceptions from `async void` land "directly on the SynchronizationContext that was active when the async void method started" and cannot be caught with catch. Also: "Some events also assume that their handlers are complete when they return", and "async lambdas should only be used if they're converted to a delegate type that returns Task" ([article](https://learn.microsoft.com/en-us/archive/msdn-magazine/2013/march/async-await-best-practices-in-asynchronous-programming)). For OpenSmi this means: the events come from the dispatch loop without a SynchronizationContext. An exception from an `async void` handler then lands on the ThreadPool, and an unhandled exception there terminates the process in .NET (the last step is standard runtime behavior and is not backed by this source).
- Async events in Microsoft libraries: the BCL has no `AsyncEventHandler`, and I found no dotnet/runtime proposal (**unverified**). Microsoft itself does depart from "void", though. Azure.Core uses `SyncAsyncEventHandler<T>` (sequential, exceptions isolated, `CancellationToken` in the args, [API](https://learn.microsoft.com/en-us/dotnet/api/azure.core.syncasynceventhandler-1?view=azure-dotnet)), SignalR uses `event Func<Exception?,Task>` with the explicit reasoning "without using `async void`" ([docs](https://learn.microsoft.com/en-us/aspnet/core/signalr/dotnet-client)). Visual Studio has `Microsoft.VisualStudio.Threading.AsyncEventHandler<T>` ([API](https://learn.microsoft.com/en-us/dotnet/api/microsoft.visualstudio.threading.asynceventhandler-1)).
- Leaks: "Listening for events can lead to memory leaks … this technique creates a strong reference from the event source to the event listener" ([Weak event patterns](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/events/weak-event-patterns)).
- Channels: `BoundedChannelFullMode` has `Wait` (default), `DropNewest`, `DropOldest` and `DropWrite`, plus an `itemDropped` callback. "Whenever a … Writer produces faster than a … Reader can consume, the channel's writer experiences back pressure." ([Channels](https://learn.microsoft.com/en-us/dotnet/core/extensions/channels))
- Rx: the only built-in backpressure is that `OnNext` has to return before the next call comes. This rule is also the serialization guarantee, but it does not hold across scheduler boundaries ([Intro to Rx](https://introtorx.com/chapters/key-types)). On Windows TFMs, System.Reactive 6 pulled in the desktop runtime, which grew a self-contained app from 90.8 MB to 182 MB. Only 7.0 (2026-07-17) splits the package ([ADR 0005](https://github.com/dotnet/reactive/blob/main/Rx.NET/Documentation/adr/0005-package-split.md), [Release](https://github.com/dotnet/reactive/releases/tag/rxnet-v7.0.0)).

## 3. Comparison

In what follows, "async event" means a C# `event` with a Task-returning delegate, awaited sequentially, with exceptions isolated per handler (RabbitMQ/Azure.Core style). "Hybrid" means async event plus `IAsyncEnumerable` watch plus `WaitFor…Async`.

**Threading and ordering.** With events, both depend on the raiser. OpenSmi raises from a serial loop, so notifications arrive in the same order as in the queue. Sync events and sequential async events also keep the order of the handlers. Today's `AsyncSignal` (`Task.WhenAll`) does start the handlers in registration order, but a handler may not yet see the next event because the loop waits for the slowest one. With WhenAll there is no ordering within one event. Rx guarantees serialized `OnNext` per observer ([Intro to Rx](https://introtorx.com/chapters/key-types)); the observer docs explicitly leave the order between observers open ([Observer](https://learn.microsoft.com/en-us/dotnet/standard/events/observer-design-pattern)). `IAsyncEnumerable` over one channel per subscriber: FIFO per reader, each reader runs on its own flow and does not hold up the others.

**Exceptions.** With a plain multicast `Invoke`, the chain stops at the first error and the exception is thrown into the dispatch loop. To isolate errors, you iterate `GetInvocationList()` yourself, as RabbitMQ does in [AsyncEventingWrapper](https://github.com/rabbitmq/rabbitmq-dotnet-client/blob/main/projects/RabbitMQ.Client/Impl/AsyncEventingWrapper.cs). MQTTnet does not do this: if a handler throws there, the remaining ones do not run ([AsyncEvent.cs](https://github.com/dotnet/MQTTnet/blob/master/Source/MQTTnet/Internal/AsyncEvent.cs)). `async void` handlers on sync events escape any isolation (section 2). With Rx, an `OnNext` throws in the subscriber itself. Rx can report an error only once through `OnError`; after that the sequence is terminated. With `IAsyncEnumerable`, exceptions are thrown in the consumer's `await foreach` loop, which is where the consumer can handle them. They do not reach the producer.

**Async handlers.** Sync events do not support them, only `async void`. Async events support them directly, and the caller waits for them. Rx needs `SelectMany`/`Concat` constructs for this (learning curve). With `IAsyncEnumerable`, the consumer can naturally write `await` in the loop body.

**Unsubscribing and leaks.** With events, `-=` needs the same delegate instance, so lambdas can only be unsubscribed if you keep them in a variable. The source holds on to the listener ([Weak events](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/events/weak-event-patterns)). Because `RemoteSkill` and co. live as long as the connection, this matters for short-lived ViewModels. Rx returns one `IDisposable` per subscription, and SignalR does the same for `On` ([HubConnection.cs:385](https://github.com/dotnet/aspnetcore/blob/main/src/SignalR/clients/csharp/Client.Core/src/HubConnection.cs)). With `IAsyncEnumerable` the subscription ends with the loop (break, token, dispose of the enumerator). A forgotten subscription cannot happen this way, but an enumerator that is never read to the end keeps its buffer.

**Backpressure and slow consumers.** With sync and async events, a slow handler blocks the shared dispatch loop, and with it all notifications of the client. SignalR, MQTTnet and NATS accept this. They buffer without limit in front of the loop (SignalR `Channel.CreateUnbounded`, MQTTnet `AsyncQueue`, NATS `_eventChannel`). Rx has no real backpressure (section 2). With `IAsyncEnumerable` and a bounded channel per subscriber, a slow reader only slows itself down. The overflow strategy can be chosen explicitly, and losses can be counted (NATS `MessageDropped`, OPC Foundation `DroppedNotificationCount`).

**Dependencies.** Events and `IAsyncEnumerable`/channels are part of the BCL. Async events need their own delegate type (one line) or `Func<…,Task>`. Real Rx needs System.Reactive; see the size effect before 7.0 ([ADR 0005](https://github.com/dotnet/reactive/blob/main/Rx.NET/Documentation/adr/0005-package-split.md)). `IObservable<T>` alone is BCL, but is of little use without Rx operators.

**Testability.** With async events, the test awaits the raiser and then knows that all handlers are done (Azure.Core: "The event handlers will finish before returning control"). With sync events and `async void` it does not know that ([Cleary](https://learn.microsoft.com/en-us/archive/msdn-magazine/2013/march/async-await-best-practices-in-asynchronous-programming): "Async void methods are difficult to test"). With `IAsyncEnumerable`, `await stream.FirstAsync(pred).WaitAsync(timeout)` works (`System.Linq.AsyncEnumerable` is part of the BCL from .NET 10 on, **unverified**; otherwise a package or a hand-written loop). For Rx there is `TestScheduler`, which makes it the most powerful option, but also the most laborious one.

**Ergonomics.** In a UI, sync events are the most familiar (FDG usability). Because OpenSmi does not raise on the UI thread, though, the user has to marshal, as in the SignalR example with `Dispatcher.Invoke` ([docs](https://learn.microsoft.com/en-us/aspnet/core/signalr/dotnet-client)). An async event costs only a `return Task.CompletedTask;`. Rx shines with `ObserveOn` in the UI, but brings a dependency and a learning curve. In a worker or orchestrator, async events fit "on every X, react async". For "wait for X" and "process in order", `IAsyncEnumerable` is clearly better, because cancellation, timeout and exceptions sit in the caller's control flow. In scripts, `await skill.WaitForStateAsync(...)` or `await foreach` is the shortest; event handlers are awkward there.

**Fit for "wait until state X".** With events there is a race between query and registration, and you need TCS tricks, like `WaitForStatesAsync` today ([RemoteCallable.cs](../../../src/OpenSmi.Client/RemoteCallable.cs)). Rx solves this with `BehaviorSubject` + `FirstAsync(pred)`. An `IAsyncEnumerable` that delivers the current value first solves it with `TakeUntilAsync`. This is exactly what the OPC Foundation built the stream for ([Subscriptions.md](https://github.com/OPCFoundation/UA-.NETStandard/blob/2.0.0/docs/Subscriptions.md)). One trap applies to all event variants with an awaited serial dispatch loop, including today's `AsyncSignal`: if a handler waits for a future notification of the same client (e.g. `await other.StartAsync(StartWait.Completion)` in the `StateChanged` handler), it hangs until the timeout. The loop waits for it, and the expected notification is stuck behind it in the queue. A stream consumer runs outside the loop and does not have this problem. I derived this from the code and did not test it.

## 4. Recommendation

**Hybrid: async events for "react to every change", plus `Watch…Async` as `IAsyncEnumerable` for consuming and waiting. The existing `WaitFor…Async` stay.** No Rx and no custom `AsyncSignal` type.

Rationale: the comparable network clients have almost all switched from sync handlers to Task-returning events (MQTTnet 4, RabbitMQ 7, Azure IoT v2). SignalR and Azure.Core, both from Microsoft, explicitly give `async void` as the reason. OpenSmi's consumers are mostly async workflows, and the events come from a loop without a SynchronizationContext, where an `async void` error can take down the process. That is why, unlike the assessment in ticket 25, I advise against plain `EventHandler<T>`. The FDG "void" rule dates from 2008, and Microsoft itself no longer follows it in newer client libraries. The `IAsyncEnumerable` part covers what events do poorly: waiting without a race, cancellation and timeout in the control flow, a separate buffer per reader so that a slow reader does not hold up the others, and scripts without handler code. This is the same division of labor that OPC Foundation 2.0 (handlers + `IStreamingSubscription`) and NATS (connection events + `SubscribeAsync`) chose.

Anyone who wants zero custom types and maximum FDG conformance can use `EventHandler<T>` instead of the async delegate, with the same hybrid next to it (the OPC Foundation Classic way). Then the docs have to state clearly: no `async void`, async work belongs in `Watch…Async`.

Minimal API (names are suggestions):

```csharp
// one line, like RabbitMQ/NATS; Task instead of ValueTask for simple lambdas
public delegate Task AsyncEventHandler<in TEventArgs>(object sender, TEventArgs e);

public sealed class SkillStateChangedEventArgs(SkillState oldState, SkillState newState, CancellationToken ct) : EventArgs
{ public SkillState OldState => oldState; public SkillState NewState => newState; public CancellationToken CancellationToken => ct; }

// RemoteSkill
public event AsyncEventHandler<SkillStateChangedEventArgs>? StateChanged;
public IAsyncEnumerable<SkillState> WatchStateAsync(CancellationToken cancellationToken = default); // delivers CurrentState first
public Task WaitForStateAsync(SkillState target, TimeSpan? timeout = null, CancellationToken cancellationToken = default); // unchanged

// RemoteVariable
public event AsyncEventHandler<ValueChangedEventArgs>? ValueChanged;           // ValueChangedEventArgs(Variant Value, ...)
public IAsyncEnumerable<Variant> WatchValueAsync(CancellationToken cancellationToken = default);

// RemoteLock
public event AsyncEventHandler<LockOwnerChangedEventArgs>? LockingUserChanged;
```

Semantics that have to be defined:
1. Events are raised from the serial dispatch loop; the handlers run one after the other in registration order and are awaited. Exceptions are logged per handler, and the remaining handlers keep running (RabbitMQ or Azure.Core semantics). `OperationCanceledException` during shutdown is ignored.
2. `Watch…Async` creates a bounded channel per call (proposal: `DropOldest`, small capacity; for state and value the newest one counts). The first entry is the current cache value. The stream ends with the token or when the client is disposed. Lost entries are logged or counted.
3. The docs say: handlers must be short and must not wait for future notifications of the same client. That is what `Watch…Async` and `WaitFor…Async` are for.

What changes compared to today:
- `AsyncSignal<T>` and `Connect`/`Disconnect` are dropped; `+=`/`-=` on C# events take their place. The signatures change from tuples `(Sender, X)` to `(object sender, XxxEventArgs e)`. This breaks all current callers and the internal `AutoLock`.
- The handlers run sequentially instead of in parallel (`Task.WhenAll`). The latency per notification is then the sum of the handler times instead of the maximum. In return, the order is deterministic.
- The isolation of exceptions stays (they are logged today as well).
- New: the `Watch…Async` streams with their own buffer and a defined loss policy. Until now there was no pull API.
- Unchanged: the serial dispatch loop away from the SDK thread, `WaitForStateAsync` with TaskCompletionSource, and the deadlock trap for handlers that wait for future notifications. The trap is now documented instead of hidden.
